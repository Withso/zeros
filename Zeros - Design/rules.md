# Zeros Design
meta/design.toml registers this directory; meta/canvas.json owns its pages and canvas metadata. Commit this folder together. Do not gitignore it.
For authorized local Design edits, use normal Read, Write, Edit, patch or Bash tools to author HTML, CSS, assets and meta/canvas.json. No API apply, publish or mode switch is required. Cloud executions follow their composer authoring policy.
Code agents may inspect or edit this folder when the user's request calls for it. The Design tag sets the default editing target; an attached frame in Code context is normally a reference for application implementation. Provider permissions and Plan still apply.
Each page has its own folder. Create a frame by writing <page.folder>/<name>.html and adding its stable ID to meta/canvas.json frames and that page's frames array. Example frame: {"kind":"html","source":"page-1/home.html","title":"Home","x":0,"y":0,"width":390,"height":844}.
Add a page natively by appending a page record to meta/canvas.json pages and create the folder at the Design root. Example: {"id":"checkout","title":"Checkout","folder":"checkout","frames":[]}. Use a unique stable ID and title; folder must be one portable segment (1-64 letters, digits, dots, underscores or hyphens; start with a letter or digit, no trailing dot). A lowercase slug is recommended. Folder names must be unique case-insensitively, must not be meta, assets or components in any case, and must not collide with another root entry. Keep 1-64 pages and at most 256 frames across the whole directory. Each frame ID belongs to exactly one page and its source stays inside that page's folder. Page rename changes the title only; preserve its folder.
Keep directory, page and frame IDs and unrelated metadata. Patch existing source; canvas dimensions set its viewport. Design frames render HTML, CSS and supported local assets. Use CSS @keyframes for animation and CSS transitions for visual states. Authored scripts, inline event handlers, JSX/TSX and application logic do not run in a frame. Represent controls as visual states; live components will use separate Code layers. Normal shell, Node and Python tools may generate and validate source. Preserve stable frame IDs and viewport dimensions, and verify the actual rendered frame. When implementing an application from a frame reference, follow that application's normal source and runtime conventions. Only listed HTML files are frames. Shared tokens.css, components and assets stay at the Design root; link ../tokens.css from a page's HTML frame. Resolve frame HTML and CSS references relative to the containing source file; component HTML references stay relative to the Design root.
Use Zeros Settings or Design mode lifecycle tools to create, migrate or remove registration. Preserve IDs when repairing existing source conflicts. Design API inspect, styles, validate and capture are optional helpers; visual controls edit the same source.
Save sources before canvas references. Re-read changed files before edits; do not overwrite concurrent work. Normal authorized Git operations integrate these same checkout files; saving never auto-commits.

## Zeros product designs

This directory holds mockups of the Zeros desktop app itself. docs/design-system.md is the normative guide (§11 covers this directory); these rules adapt it to frames.

- meta/canvas.json imports the app's own styles: styles/zeros-tokens.css as a tailwind source (compiled for each frame's classes) and styles/semantic-tokens.css as a css source. Every frame receives them automatically; keep both declarations. Prefer the app's Tailwind utilities (bg-bg2, p-3, rounded-md, text-xs) over custom classes, and never reuse a utility's name for a custom class.
- tokens.css is generated from styles/tokens by `pnpm design:docs`. Never edit inside its @generated regions, paste token values into a frame, or change a product token in the theme editor; product token changes go to styles/tokens/*.tokens.json. An unadopted idea stays in that frame's own <style>, and the frame title says "Proposal".
- Dark is the canvas Base theme; Themes → light previews Light. Review both. Don't author data-theme or data-zd-theme; the canvas applies the theme.
- Surfaces: --bg1 app canvas, --bg2 raised or composer, --sidebar-bg repository sidebar, --bg3 only for floating menus and popovers (with --border2 and --shadow-dropdown). Hover uses the surface's -hover token; selected is the hover state that stays.
- Text: --fg1 emphasis and selected, --fg2 default, --fg3 secondary and placeholders, --muted-fg metadata. Never fake a tier with opacity. On --<family>-bg use --<family>-fg, and pair status color with an icon or text.
- Type: --text-xxs 10, --text-2xxs 11, --text-3xxs 12, --text-xs 13 on an 18px line, --text-sm 14 on a 20px line; weights --weight-medium, --weight-semibold, --weight-bold. Frames render Geist and Geist Mono through the app style source, whose Tailwind entry imports them (installed dependencies required); use var(--font-sans) and var(--font-mono), never a font file of your own.
- Controls are --control-height (28px) or --control-height-compact (24px), one height per row. Radius: --radius-sm (buttons, inputs, chips, menu items), --radius-md (tabs, navigation rows, small cards), --radius-lg (dialogs, cards, panels); floating menus use twice --radius-lg. Spacing uses --space-<step>, the Tailwind step: --space-3 is 12px and implements as p-3.
- Show real states: default, hover, selected, focus-visible, disabled, loading, empty, error, and long or missing content, plus Local and cloud workspace states where the surface differs (RULES.md §8). Give each state its own frame or a labelled row.
- A full window frame is 1600×1000 (the default window); check layouts that must survive the 840×700 minimum. A component frame uses its natural size. Title frames "<Surface> — <state>" and give every element inside body a stable data-oid.
- Implementing a frame keeps its utility classes and maps any remaining values to Tailwind utilities (var(--bg2) is bg-bg2), and its controls to the primitives in apps/desktop/src/renderer/shared/ui/; never copy frame CSS into a component.
- Verify each frame with the native `design validate` and `design capture` commands supplied in frame context, then inspect the PNG. Capture Dark (the default) and Light (`--theme light`).
