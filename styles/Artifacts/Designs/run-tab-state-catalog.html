Terminal pane · Run tab · State catalog

Every state the Run tab can show — and how to make it multi-run

Today “Run” is a single command typed into a shell: one script per repo, one tab, and no way to tell whether it passed or failed. This catalog is the full inventory — what ships now, and a before / after for the leap to many named actions, each with its own status — a rotating star while it runs, a green or red icon once it’s done — an icon you pick, and a header split-button to launch them.

From one “Run” to a shelf of actions Many scripts, real status, icons, one header button.

One run, or many

Launch several scripts at once — Dev, Test, Storybook — each in its own Run tab. The PTY engine already runs them concurrently; only the model says “one”.

Status you can read

Running is a rotating star; finished and failed tint the tab icon green or red — on the tab, in the header, and surviving a restart. The same status backbone Setup just got.

Actions you configure

Name it, give it an icon from a searchable grid, set its command and platforms — then launch it from one header split-button.

The running indicator — shape studio

★ New

A rotating “indianised star” means a run is live

Rather than a waveform or a coloured dot, a live run is marked by a small rotating star — a Zeros-palette gradient that spins, shimmers, and shifts colour on every turn. It replaces the status dot on Run tabs, sits beside the header Stop button, and lands on the split-button face. Finalized: Sparkle — the 4-point star — at the faster spin, shown wherever an action is running. The other shapes below are kept for reference only.

Pure CSS + an SVG mask — no images, no canvas. Colours are the real tokens; honours prefers-reduced-motion.

How it behaves
  • Shown only while a run is live. It appears when the process starts and vanishes the instant it exits — its presence is the “running” signal, so no “(exited)” text or amber dot is needed (see A3/A4).
  • Colours cycle through the palette — green → blue → violet → red → yellow — so every rotation looks a little different, and the gradient shimmers within the shape while the shape itself turns.
  • One shape everywhere: every running action wears the same Sparkle, so “that star = something is running” stays a single learnable signal; the tab’s icon and label carry the which-action distinction (see B1/B2).
  • Reduced motion: rotation, shimmer, and pulse stop; a slow colour cycle remains so the signal never disappears entirely.

A4 Ships today Changes

Run exited — success and failure look identical

When the shell exits, the tab gains a dim “(exited)” suffix and the body prints [process exited with code N] — press any key to restart. That exit code is the only pass/fail signal, and it’s never stored — a code 0 and a code 1 look the same.

No pill, no color, no persistence. Pressing any key restarts.

Part B — Gaps to build · before → after

B1 Gap → proposal

Run many scripts at once

Today only one run exists — a single scripts.run string and one deterministic pty-run-<hash> session that every launch reattaches to. After: each configured action gets its own Run sub-tab and its own PTY, so Dev, Test, and Storybook run side by side. The engine already supports unlimited concurrent terminals — plain terminals prove it.

The cap is the data model, not the engine. One id per action, not per folder.

B4 Gap → proposal

Give Run a real status — running / finished / failed

“How is the run status captured?” Today: it isn’t — only a boolean alive and a throwaway exit line. After: Run borrows Setup’s exact status language — a filled outcome badge (green finished / red failed) and a tab-icon tint — driven by the real exit code.

A one-shot action reports pass/fail; a long-lived dev server shows “running” until you stop it.

Before: pass and fail are visually identical; the exit code lives only in dim body text and is discarded. Nothing on the tab, in the header, or after restart tells you the verdict.
After: a RunManager (mirroring SetupManager) captures running → finished | failed | stopped from the exit code, shows the 24px filled badge + “Rerun”, and marks the tab — a rotating star while running, then a green / red icon — the identical rule Setup uses.
Status rules (shared with Setup)
  • Long-lived vs one-shot: a dev server has no meaningful exit while alive → it shows the rotating star and a Stop control, not a verdict. A one-shot (test/build) resolves to finished/failed.
  • The tab carries the state on its icon — a rotating star while running, then the icon tints green (finished) or red (failed). No separate dot; the star clears on exit, the colour persists until the next run.
  • Stopped is not failed: hitting Stop records stopped (neutral) — the icon returns to its normal colour, not red.
B5 Gap → proposal

Status that survives a restart

Run state is in-memory only; on reload alive is forced back to true and the command never re-fires — so a finished or failed run comes back looking idle, as if it never ran. After: the last outcome is remembered per action and shown as a compact summary with a timestamp and “Run again”.

The result is durable (a DB row); only the live log is transient.

Part C — Container context

C1 Context · ships today

Worktree missing — the whole panel is replaced

If the workspace folder is gone from disk, the entire 3-column shell — Run tabs included — is replaced by a recovery screen. No Run state can render here; noted so the redesign doesn’t try.

Panel-level state that supersedes every Run tab.

C2 Context · ships today

No host connection — a run can’t spawn

In web/dev mode with no paired Mac app or relay, the PTY can’t be created, so a Run tab shows a yellow notice instead of a shell. Any run status (B4) must degrade gracefully to this — there’s nothing to report until a host is present.

The run affordance depends on a live PTY host.
