Project settings · Files to copy · Design

Choosing which ignored files ride along — without knowing what a glob is

A new workspace branches from origin/main, so it contains only what Git tracks. Every gitignored file the project needs to run — .env, local config, certificates — is missing. This is the surface that decides what gets carried over, designed so someone who has never written a .gitignore can get it right on the first try.

Show the files, not the syntax Patterns stay — one click away, for people who want them.

The answer is already on screen

The pane opens having already scanned the project. You tick real files you can see, with their sizes — you never type a pattern and hope.

Every risky row says so

“Only pick gitignored, untracked files” stops being a rule to remember. Not-ignored, already-tracked and matches-nothing are labels on the row.

Always show the outcome

Committed file, app setting or built-in default — the resolved list is rendered the same way, because that answer is what the user came for.

Advanced — use file patterns instead
Pre-ticked, not silently defaulted. The built-in default is .env*, and any saved list replaces it. Turning that default into visible ticked rows is what stops someone losing their .env the first time they touch this screen.
Grouping is derived, not configured. Env / tool-config / other comes from the resolved paths — no taxonomy for the user to learn, and a project with only .env shows one group.

A3 Proposed

Advanced — patterns, expanded

The escape hatch for anyone who wants .env* or certs/**. The same box other tools ship, plus a per-line match count so a wrong pattern is obvious the moment you stop typing.

Ticking boxes in simple mode writes into this same list. One setting, two editors — never two sources of truth.

Plain .gitignore syntax — # comments, * wildcards, ** for any depth, a leading / to pin to the project root, ! to take something back out. Matched by git itself, so it behaves exactly as it does in a .gitignore: last match wins.
The counts are the feature. A count of 0 is the typo signal; a negation shows how many files it actually removed, so a dead ! line reads as dead instead of looking load-bearing.

B3 Divergence

Part D — Behind the pane

D1 Backend landed

Where the value lives

The pane is per-repo. It edits exactly one thing: this project’s own list. There is no global/per-project scope switch — “which files does this project need” has no sensible cross-project answer, and a toggle would only make people wonder which side they were looking at.

Precedence is resolved in the engine; the pane reports which source won and edits only its own.
Priority Source Scope Editable here?
1 — highest .worktreeinclude at the project root Committed. Whole team, every machine. Read-only + Open file (B2)
2 — what this pane writes file_include_globs in .zeros/settings.local.toml This project, this Mac. Gitignored. Yes — the only editable source
3 file_include_globs in ~/.zeros/settings.toml Every project, this Mac. No — hand-edited TOML only
4 — fallback Built-in default .env* Everywhere, until you change something. —
Set anything and .env* stops applying. That is why A1 pre-ticks the env files it finds: turning the invisible default into visible, explicit rows is what stops someone losing their .env the first time they open this pane.
Row 3 stays readable, not writable. The engine still resolves a hand-edited global list, and the pane labels it as inherited when it wins — but saving here always writes this project’s file, so a per-project edit can never silently change every other repo.
Writes go through the existing settings path. settings.write with { file_include_globs: [...] } against the repo-local layer; null clears this project’s list and falls back to whatever is below it. No new write path, no new file format.
D2 Backend landed

What the UI needs from the engine

One read call. Every state in Parts A–C is a render of this one response — including the warning pills, the per-line counts and the “couldn’t check” case.

filesToCopy.preview — desktop-only; it expands patterns into real gitignored paths. 
// engine op — one call renders the whole pane
filesToCopy.preview { repoRoot, patterns? } →

  source         "worktreeinclude" | "file_include_globs" | "default"
  sourceLayer    "repo-local" | "user" | "team" | …   // labels an inherited list
  sourcePath     // absolute path of .worktreeinclude, when it won
  sourceText     // its raw text, for "Show patterns" (B2)
  rootPath       // the folder files are copied FROM
  patterns       [{ raw, negate, line, matchCount }]  // A3 · B3
  files          [{ path, bytes, ignored }]           // A1 · A2
  trackedMatches [ path ]                            // "Already in every workspace"
  totalCount / totalBytes / truncated              // C2
  warnings       [ string ]
  complete       true | false                        // false → C4, never "0 files"
Drafts are previewable. Pass patterns to preview the unsaved textarea — including an empty array, which means “the box is cleared”, not “use the saved list”. A committed .worktreeinclude ignores the draft, because previewing something create won’t use would be a lie.
Desktop-only, deliberately. The op expands patterns into the real on-disk set of gitignored paths plus sizes — exactly what the file tree filters out for paired devices. A remote pane would need its own filtered shape, not this one.
D3 Needs a decision

Open questions

Four calls I’d rather make with you than for you. Each one changes the markup above, so they’re cheap now and expensive later. (Scope is settled: the pane is per-repo, no global toggle.)

Answers here unblock the React implementation.
  • Does simple mode write filenames or patterns? Ticking .env and .env.local could store the two exact names, or collapse to .env*. Exact names are honest and predictable; .env* keeps working when you add .env.staging next week. Proposal: store exact names, plus a one-click “copy every .env file, including new ones” chip that swaps in the pattern.
  • Auto-tick on first open, or ship the built-in default until touched? Auto-ticking means the rows shown are the rows used. Not auto-ticking means the pane can be opened and closed with zero risk. A1 auto-ticks and marks them Recommended.
  • Is .worktreeinclude creatable from the app? A “Share this list with the team” button that writes the file would be genuinely useful — and would immediately make the setting read-only, which needs saying out loud before the click.
  • Where does this pane live? Rendered above as its own Files tab on the project page. The alternative is folding it into Paths, which already edits per-project, this-Mac settings — at the cost of burying it.
