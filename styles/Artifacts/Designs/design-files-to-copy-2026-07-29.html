Project settings · Files to copy · Design

Choosing which ignored files ride along — without knowing what a glob is

A new workspace branches from origin/main, so it contains only what Git tracks. Every gitignored file the project needs to run — .env, local config, certificates — is missing. This is the surface that decides what gets carried over, designed so someone who has never written a .gitignore can get it right on the first try.

Show the files, not the syntax Patterns stay — right under the list, for people who want them.

The answer is already on screen

The pane opens having already scanned the project. You tick real files you can see — you never type a pattern and hope.

The files are the content

No group taxonomy, no item counts, no sizes, no row badges. Folders, closed, with names in them. Everything else was the pane talking about itself.

Always show the outcome

Committed file, app setting or built-in default — the resolved list is rendered the same way, because that answer is what the user came for.

Pre-ticked, not silently defaulted. The built-in default is .env*, and any saved list replaces it. Turning that default into visible ticked rows is what stops someone losing their .env the first time they touch this screen — the first tick writes out everything currently matched as explicit lines, so the rows on screen become the rows in the file.
The editor is empty on purpose here. It shows this project’s list, and this project has none yet — the tick above comes from the inherited .env*. Pre-filling the box with a default nobody wrote is how the phantom counts in A4 happened; leaving it empty keeps “what I have set” and “what is in effect” from being drawn as the same thing.
One heading, no taxonomy. These were three cards — Environment & secrets, Tool & editor config, Other ignored files — each with a coloured glyph, a Recommended pill and an item count. Every one of them was the pane talking about itself. The files are the content.
No sizes. They were argued for as the thing that stops someone ticking a 2.1 MB coverage report. In practice they put a right-aligned number on every row — and an em-dash on every folder, because a collapsed directory is never walked — to inform a decision that node_modules/ already announces by name.
Folders first, then files, alphabetical. Fixed, so the list never reshuffles as a scan lands.
A2 Proposed

Folders, and the one rule that makes closing them safe

Git hands us a flat list — lib/api-zod/node_modules/, lib/db/node_modules/, artifacts/zdocs/dist/ — which is two or three real directories wearing two dozen rows. Closing them is obvious. What is not obvious is what happens to a file you already ticked.

A closed folder that hides a tick is a file you cannot find again to untick. That is the failure this rule exists to prevent.

A partly-ticked folder still shows what is ticked inside it. Closed, lib/ is one row with a dash in its box — “some of this”, which is useless on its own. So the rows that are ticked come up with it, labelled relative to the folder that surfaced them. Collapsing hides only what is unselected.
A fully-ticked folder stays one row. Its own box already says “all of this”, so there is nothing hidden and nothing to surface — otherwise one click on a closed folder would burst it into every file it holds. Same reason a wholly-ticked subfolder comes up as one row (db/) rather than as its three files.
A folder with one thing in it is that thing. scripts/ → node_modules/ is a triangle that hides nothing, so the chain merges into a single row reading scripts/node_modules/. Same for lib/api-spec/node_modules/ above.
Ticking a folder writes one line per file, not one line for the folder. A saved /lib would match everything ignored under it forever — including things added next week — and would lock every row underneath behind an ancestor no checkbox can remove.
A3 Proposed

The pattern editor, open

For anyone who wants .env* or certs/**. The same box other tools ship, plus a per-line match count so a wrong pattern is obvious the moment you stop typing. It sits under the list, always visible — it used to hide behind an Advanced — use file patterns instead disclosure, which is a fair description of the box and a poor way to find it.

Ticking boxes above writes into this same list. One setting, two editors — never two sources of truth.

Plain .gitignore syntax — # comments, * wildcards, ** for any depth, a leading / to pin to the project root, ! to take something back out. Matched by git itself, so it behaves exactly as it does in a .gitignore: last match wins.
The counts are the feature. A count of 0 is the typo signal; a negation shows how many files it actually removed, so a dead ! line reads as dead instead of looking load-bearing.
Comments get no count. A # line matches nothing by design, and the engine scores it 0 like any other line — so the pane was printing a red zero and the words matches nothing beside the user’s own note. Comment lines are dropped from the list entirely; they are prose, not patterns. Same rule as A4, one level down: only say something about a line when there is something true to say.

Why it happened. With no list of its own, the project inherits the built-in .env*. The editor renders your list — which is nothing — while the counts came from the resolved one. Two sources of truth, one screen.

“Nothing will be copied will be copied from …”. The same row had the summary sentence completing a lead that was already a whole sentence. The lead is a noun phrase in both branches now — Nothing / 3 files — and the row reads once.

B3 Divergence

A pattern that matches nothing looks identical to one that works

With only a total count, certs/*.pem matching zero files is invisible — the total just reads lower than you expected, if you were counting at all. The failure surfaces days later, when a workspace won’t start.

Per-line counts come from the same preview call; no extra user action.

C5 Proposed

What actually pops up at the bottom

The pane used to grow yellow callouts under the list — the empty list, the display cap, the byte total, the failed scan — none of which were toasts, all of which read as one. They are gone. What is left is the app’s real toast surface: a fixed 350 px card at the bottom-right of the window, and this pane raises exactly one of them.

apps/desktop/src/renderer/shared/ui/primitives/elements/toast.tsx · bottom-right, 24 px offset, 3 visible, errors 6 s.
Couldn’t save which files to copy

The neighbours it stacks with — same card, raised by the workspace it is about to seed, so this is the whole vocabulary a user sees around this feature:

Couldn’t create workspace: …
The engine rolled the incomplete checkout back safely. Create it again to retry.
Workspace creation is taking longer than usual
It’s still being created in the background.
One toast, and it is a write failure. Saving is a debounced autosave with no button to watch, so a failed write is the one thing that genuinely has no other place to appear. Everything else the pane knows is a fact about the list, and facts about the list belong beside the list.
It was going through the wrong door. This pane called sonner directly instead of the app wrapper. The global <Toaster> is mounted unstyled and strips sonner’s own chrome, so the only toast this feature could raise painted as bare unstyled text — no card, no padding, no dismiss. It now goes through toast from ui/primitives, like every other caller.
Engine warnings are not toasts. preview.warnings still comes back — cut-short scans, the candidate cap, the byte total — and the seeding path still logs them. The pane no longer paints them: an advisory the user cannot act on is noise, and the one that matters (an incomplete scan) is already the summary line in C4.
No “Reset to default”. The link beside the summary emptied the whole list in one click, next to the sentence that told you how many files you were about to lose. Unticking is the way back, one row at a time, and it is undoable by re-ticking.

Part D — Behind the pane

D1 Backend landed

Where the value lives

The pane is per-repo. It edits exactly one thing: this project’s own list. There is no global/per-project scope switch — “which files does this project need” has no sensible cross-project answer, and a toggle would only make people wonder which side they were looking at.

Precedence is resolved in the engine; the pane reports which source won and edits only its own.
Priority Source Scope Editable here?
1 — highest .worktreeinclude at the project root Committed. Whole team, every machine. Read-only + Open file (B2)
2 — what this pane writes file_include_globs in .zeros/settings.local.toml This project, this Mac. Gitignored. Yes — the only editable source
3 file_include_globs in ~/.zeros/settings.toml Every project, this Mac. No — hand-edited TOML only
4 — fallback Built-in default .env* Everywhere, until you change something. —
Set anything and .env* stops applying. That is why A1 pre-ticks the env files it finds: turning the invisible default into visible, explicit rows is what stops someone losing their .env the first time they open this pane.
Row 3 stays readable, not writable. The engine still resolves a hand-edited global list, and the pane labels it as inherited when it wins — but saving here always writes this project’s file, so a per-project edit can never silently change every other repo.
Writes go through the existing settings path. settings.write with { file_include_globs: [...] } against the repo-local layer; null clears this project’s list and falls back to whatever is below it. No new write path, no new file format.
D2 Backend landed

What the UI needs from the engine

One read call. Every state in Parts A–C is a render of this one response — the tree, the tick state, the per-line counts and the “couldn’t check” case. It returns more than the pane now draws; that is deliberate, and the unpainted half is listed below rather than deleted, because a size or a warning is cheap to re-surface and expensive to re-derive.

filesToCopy.preview — desktop-only; it expands patterns into real gitignored paths. 
// engine op — one call renders the whole pane
filesToCopy.preview { repoRoot, patterns? } →

  source         "worktreeinclude" | "file_include_globs" | "default"
  sourceLayer    "repo-local" | "user" | "team" | …   // labels an inherited list
  sourcePath     // absolute path of .worktreeinclude, when it won
  sourceText     // its raw text, for "Show patterns" (B2)
  rootPath       // the folder files are copied FROM
  patterns       [{ raw, negate, line, matchCount }]  // A3 — only while they ARE the box (A4)
  files          [{ path, bytes, ignored }]           // decides which boxes are ticked
  candidates     [{ path, isDir, bytes }]             // the tick-box universe → the tree
  totalCount     // the one number the pane prints
  complete       true | false                        // false → C4, never "0 files"

  // still returned, no longer painted:
  totalBytes / truncated / bytes  — sizes came off every surface (A1)
  trackedMatches                 — the "already tracked" line came off
  warnings                       — the yellow callouts came off (C5)
Drafts are previewable. Pass patterns to preview the unsaved textarea — including an empty array, which means “the box is cleared”, not “use the saved list”. A committed .worktreeinclude ignores the draft, because previewing something create won’t use would be a lie.
Desktop-only, deliberately. The op expands patterns into the real on-disk set of gitignored paths plus sizes — exactly what the file tree filters out for paired devices. A remote pane would need its own filtered shape, not this one.
D3 Settled

Questions this artifact used to ask

Four calls that were open when the pane was drawn. Three are answered by what shipped; the fourth is still worth having.

Kept so the reasoning survives the decision.
  • Does simple mode write filenames or patterns? Exact names. Ticking writes the anchored literal /apps/control-plane/.env, one line per file — including when you tick a folder. It is what makes every row underneath independently untickable afterwards, which a folder-wide /lib would not be. A .env* that keeps working as you add .env.staging is still available: type it in the pattern editor, which is now visible without hunting for it.
  • Auto-tick on first open, or ship the built-in default until touched? Auto-tick. The rows shown are the rows used. What went with it is the Recommended pill that announced the fact — a ticked box in a list of unticked ones does not need a label explaining that it is ticked.
  • Where does this pane live? Its own Files tab on the project page, as drawn in A1.
  • Is .worktreeinclude creatable from the app? Still open. A “Share this list with the team” button that writes the file would be genuinely useful — and would immediately make the setting read-only (B2), which needs saying out loud before the click, not after it.

Visual design reference for “Files to copy”. Checkboxes, chevrons and buttons demonstrate placement and hierarchy; nothing in this artifact copies a file. Colors, radii and type are pulled from Zeros Foundation (Zeros Shade dark + Light) — toggle the theme in the header to check both. Revised 2026-07-30: the group cards, item counts, sizes, row badges, inline callouts, the “already tracked by Git” line, “Reset to default” and the Advanced disclosure are gone; the list is a folder tree, and the only toast left is C5.
