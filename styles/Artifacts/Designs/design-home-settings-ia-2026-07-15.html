Home tab & Settings · Consolidation proposal · 2026-07-15 · v3

Sidebar for destinations, Settings for configuration — a repo is yours, the org gets a link

Eight builds that turn the two-row Home rail into the app's front door (repos, profile — the Figma shape), make the repo page the hub for its workspaces and its settings, reorganize global Settings by scope, and retire the inline settings.toml code view. v2 after founder review: the Dashboard is untouched, collaboration is org-only for now (teams deferred — later they're just named subsets of org members), and every repo setting is managed on the repo, not in a global tree. v3 (pre-H1): no sharing UI for now — the UI writes personal layers only; hand-committed .zeros/settings.toml keeps working; future sharing is cloud-DB-primary with opt-in repo materialization, and env vars are never shared.

The one rule Sidebar = places you go to work. Settings = things you adjust and leave.

The storage is already right — the words are wrong

User prefs + keys live on the Mac; repo config travels via git; org settings + secrets live in the cloud DB. But the UI calls the committed repo file "Team", calls the MDM file "Org", and gives the real cloud org layer no label at all. Rename once, everywhere.

The repo page owns everything about the repo

A repo is personal to the user — a clone on their Mac. Its page manages both its workspaces AND all its settings (Personal + Shared lenses) in place. Sharing gives the org a discoverable link, never ownership — code and access stay with GitHub.

settings.toml is an API, not a page

The file stays first-class for agents and power users — published schema, live watcher, comment-preserving writes. The UI just stops embedding a code editor and offers "Open in Finder / editor" instead.

R6 Reference

Where every setting lives — the answer to "how are we going to store it?"

Three homes, all already built: this Mac (user TOML + OS keychain), the git repo (committed + gitignored files), and the cloud (Railway control plane). Org-shared settings ride two existing channels — the committed repo file travels with the code; the org doc + secrets vault travel with the account. No new storage system is needed; the redesign only names what exists. Secret values never enter any TOML, ever.

resolve chain: default < user < org < repo < repo-local < workspace-local < managed
This Mac never leaves the machine
  • Personal settings — appearance, models, agent providers, personal env, personal MCP ~/.zeros/settings.toml
  • API keys & secrets — provider keys, 🔒 env values, MCP tokens, GitHub token OS keychain / safeStorage
  • Per-repo personal overrides .zeros/settings.local.toml (gitignored)
  • Auth session — main process only; refresh token never enters the renderer
  • Managed policy — IT-deployed, read-only settings.managed.toml
The git repo travels with every clone
  • Shared repo settings — scripts, git defaults, non-secret env, MCP (http), prompts .zeros/settings.toml (committed)
  • Per-branch by nature — settings can differ across branches, like code
  • Safety gates stay — stdio MCP and credential-redirect env names are dropped from this layer (hostile-clone defense)
  • Secret names only — values belong in the keychain or the org vault
The cloud follows the account / the org
  • Identity & profile — Auth0 + profiles
  • Org, members, invites — control plane (Railway Postgres); teams stay backend-only, deferred
  • Org shared settings — org_settings jsonb doc, org-wide or per-repo scope; couriered to the engine in-memory, never on disk
  • Org secrets vault — envelope-encrypted, write-only UI, decrypt-at-spawn
  • New: org_repos registry (R7) — which repos are shared into the org (a link, never ownership)
  • Later: billing, audit UI, the cloud record (chats/workspace history)

Env-var guidance surfaced in both editors: your own key → Personal 🔒 · a machine path for one repo → Personal · this repo · a non-secret default for every clone → Shared · a secret every org member needs → Organization → Secrets vault (org-wide or per-repo).

Part C — Org sharing and the collaborative future

R7 Cloud Deferred · H3 (v3 D1)

Org-shared repos — a repo is yours; the org gets a link

The ownership model, stated clearly: GitHub owns the code and access (Zeros never brokers repo permissions); you own your clone (a personal repo has no cloud presence at all); sharing gives the org one registry row — org_repos {org, name, origin_url, default_branch, icon, shared_by} — which makes the repo discoverable to org members and anchors per-repo org settings/secrets and, later, shared workspaces. It never moves code or grants access. No teams for now: everyone in the org sees shared repos. Teams return later as pure filters — named subsets of org members (a team member must already be an org member) narrowing a share via one nullable team_id. A shared repo you don't have locally offers one-click Clone with your own GitHub auth.
