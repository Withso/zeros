Carry a chat's context into the next one — one click, concise by default, readable before you spend it

A new chat tab is the one place in Zeros where you have just decided to start over — and the one place with no way to bring the last chat's context with you. This catalog specs the pill row that fixes that, the two live defects it would otherwise land on top of, and every state it can be in. Revision 2 — all nine decisions are now settled; the budget chrome, the mode switch and the staleness machinery are gone, and a hover preview has taken their place. Review-only: no code has been changed.

2 blockers · 19 states · 9 decisions locked 5 of 6 moving parts already ship Nothing here needs a new design token

One click, not four

Today: right-click the old tab → Copy full transcript → click the new tab → paste 116 KB of Markdown into the composer. The pill row collapses that to one click, and the result is a removable chip instead of a wall of text you can no longer edit around.

Honest about what it costs

A text attachment is inlined into the prompt as <file name="…">. Attaching a transcript spends real context before you type a word. The reference's row says nothing about that. Ours defaults to the concise transcript, puts the message count on the pill, and lets you read the whole thing on hover before you spend a byte of it.

Mostly assembly

The engine query, the bridge op, the backwards transcript walk, the Markdown formatter and the composer chip all exist and are tested. Two things do not work: text attachments never reach the agent, and the query orders by a column that drifts — while the column you actually want is already immutable by design.

Part 0 — Two things must be fixed before any of this works

B1 Blocker Live bug today

A text attachment never reaches the agent — it is turned into an empty image and dropped

encodeComposerAttachments (agent-chat.tsx:2691) is the only encoder handleSend uses, and it has no kind === "text" branch. Every text attachment is emitted as an image block carrying data: "".

This is not specific to transcripts. Drag a .md or .txt into the composer today and it is silently discarded — the chip renders, the send succeeds, the agent never sees the file. Build the pill row on this and clicking a pill would do visibly nothing.

The <file name="…"> wrapper exists in exactly one place — editAndResubmit (agent-chat.tsx:531) — so a .txt attached while editing an already-sent message does arrive. That asymmetry is what let the bug survive. 
// agent-chat.tsx:2691 — the only encoder handleSend calls
for (const a of localAttachments) {
  if (supportsImage || !cwd || !chatId) {
    blocks.push({ type: "image", mimeType: a.mimeType, data: a.data });   // a.data === "" for text
    …
    continue;
  }
  // non-vision path: writeImageAttachment(base64: "") → requireString throws
  //                 → caught at :2740 → console.warn → dropped
}
Where each branch loses it
  • Vision agents (Claude, Cursor, GPT-5) — the adapter computes dataB64 = "", which is falsy, so no source.url is set and the block is dropped without a warning (claude-sdk/adapter.ts:2297).
  • Non-vision + cwd — writeImageAttachment is called with an empty base64, requireString throws, the catch logs and continues.
  • Codex — writes a zero-byte temp file and forwards a bogus localImage (app-server-adapter.ts:1735).
  • Cosmetic tell — the sent bubble records kind: "image" with thumbnailUri: "data:text/plain;base64,".
Second, smaller defect on the same path: encodeComposerAttachments has no validation.ok guard, so an over-budget attachment is sent anyway — contradicting agent-attachments.ts:11-13 ("submission filters out anything not ok"). Only editAndResubmit honours it (agent-chat.tsx:530). Fix both in the same change, with a regression test per branch.
The fix is small and already written elsewhere: lift the kind === "text" branch out of editAndResubmit into a shared encoder so both paths emit <file name="…">body</file> from one place. That is one function, and it repays itself immediately — every dropped .md drop starts working too.
B2 Blocker Would ship as noise

The one query that can feed this row sorts by a column that drifts — and the column you want is already immutable

chats.summariesForFolder (engine/db/chats.ts:425) is exactly the right query — one round trip returns every chat in the folder with ≥1 user message, plus its title and agent. It ends ORDER BY chats.updated_at DESC.

But chats.updated_at is bumped only by title, settings and TOUCH_CHAT reducers — and TOUCH_CHAT has zero dispatch sites. The engine's persist-on-emit path writes chat_messages and never touches the parent row. So the sort key is effectively "when the AI title landed": near-creation order with random jitter from later renames — an order that looks meaningful and isn't.

The order you asked for — newest chat first, by creation — is the one column in this table that cannot drift. chats.created_at is deliberately excluded from the upsert's ON CONFLICT DO UPDATE set, with a comment saying why: a coerced/streaming upsert from a remote client or a desktop write-through would otherwise reset the real creation time and "corrupt sort/age" (chats.ts:203). Somebody already fought this fight for us.

It is also the only order that holds still. A background chat streaming in another tab reorders a lastMessageAt row under the cursor; creation order means the pill you were reaching for is still where you left it.
Today's query — three things wrong
  • A sort key nothing writes. See above.
  • No volume. There is no message count anywhere — not on ChatRow, not on the wire, and there is no messages.count op. So a pill cannot say how big it is without loading the whole transcript first.
  • archived = 0 is hard-coded (chats.ts:445), so closed tabs — often exactly the finished work you want to hand forward — are invisible. Per D5, open and closed is not a distinction this feature makes at all.
One order change, one aggregate
-- add to summariesForFolder's SELECT
(SELECT COUNT(*)           FROM chat_messages cm
   WHERE cm.chat_id = chats.id)      AS messageCount,
(SELECT MAX(cm.created_at) FROM chat_messages cm
   WHERE cm.chat_id = chats.id)      AS lastMessageAt
-- drop the archived predicate, and then
ORDER BY chats.created_at DESC, chats.rowid DESC
  • Cheap: both sub-selects ride idx_chat_messages_chat_ord (chat_id, ord), and idx_chats_folder narrows to one workspace before the sort.
  • The rowid tiebreak is load-bearing. created_at is INTEGER with no NOT NULL and no default, and coerceChatRow defaults a missing createdAt to 0. Legacy or coerced rows collapse to a tie; rowid is insertion order, so they still land in a stable, sensible place instead of shuffling per query.
  • messageCount is the pill's trailing number and the picker's. lastMessageAt is used only for the hover preview's "last active" line (C8) — never for ordering.
  • No rawBytes. It was there to drive the budget readout, and D6 removed that; nothing else needs it.
Do not "fix" this by bumping chats.updated_at on every message. That is the obvious repair for a dead sort key, and it is a trap: the column is pulled by delta sync (rev/db.pull), so making it move on every streamed token would push a chats-table row on every chunk. The fix costs zero writes — it is an ORDER BY edit on a column that is already correct.

Findings
  • 1 · No volume, anywhere. Five identical-looking pills; one is a three-message chat, one is 240 messages. The click that costs 200 bytes and the click that costs 30k tokens are indistinguishable. This is the single biggest gap — C1 puts the message count on the trailing edge.
  • 2 · Hard truncation with no recovery. "Audit transcript impleme…" and "Find chat transcript impl…" are not distinguishable from each other's full titles. No tooltip, no widening, no ordering cue. C8 answers this with the transcript itself on hover, not a tooltip describing it.
  • 3 · No stated order. Nothing says what the row is sorted by, so nothing tells you where to look. Ours is one rule stated once — newest chat first, by creation date (C5) — and "how long ago" moves into the hover preview, where it informs rather than decorates.
  • 4 · The added state is a Primary button. A near-white fill across N pills is several main CTAs at once; RULES Rule 4 reserves that fill for the single main action on a view. It also fights the composer's real Send button two rows below. C4 weighs three alternatives.
  • 5 · A trailing colon on a UI label. "Add chat transcripts:" reads like a form field. The pills are self-evidently the objects of the verb.
  • 6 · The label floats. It sits on its own baseline, unrelated to the provenance block above it, so the empty state becomes two unrelated fragments. C2 folds it in as a fourth row.
  • 7 · Unbounded wrap. Five pills wrap to two ragged rows. Twenty chats would push the composer down by seven rows, in a surface whose whole job is to get you typing. C6 caps at six with a real overflow affordance.
  • 8 · No pending or error state. Reading a 240-message transcript is several engine round trips at up to 60 s each. A click with no acknowledgement reads as a dead control, and a click that fails silently is worse. C3 specifies both — and C8 makes pending nearly unreachable, because opening the preview is what warms the read.
Kept from the reference, unchanged: the row lives in the empty chat (not a dialog); one click attaches; clicking again removes; the agent's mark is the pill's leading glyph; the pills read as chat titles rather than filenames. Those are the good bones.

Anatomy of a pill — a Secondary button, 24px, with volume on the trailing edge

Three things a pill deliberately does not carry
  • A size. SUM(LENGTH(payload)) is raw transcript bytes; the formatter clips every tool payload to 40 lines / 2,000 chars, so the attached file is routinely 3–10× smaller. Showing 180 KB on the pill and 28 KB on the chip one second later reads as a bug. The count cannot disagree with itself.
  • A timestamp. "2 hours ago" on six pills is six numbers to read and rank at the moment you want to start typing. It appears once, in the preview, where you have already narrowed to one chat (C8).
  • A mode. Every pill attaches the concise transcript; there is nothing per-pill to disclose (C7).
And one thing it does — on hover
Hovering does not show a tooltip about the transcript. It shows the transcript: a header line of exactly agent, count and last activity, then the text itself, scrollable. Speccing that is C8; the reason it belongs to the anatomy is that it is what lets the pill stay this small.

Rules this row has to keep
  • The row appears or it doesn't — it never skeletons. Same contract as the setup row: an unresolved read renders nothing. This block sits above a composer the user is about to type into; a placeholder is more distracting than a missing line.
  • It must not push the composer around after first paint. Read the chat list once on mount; if it lands late, the row appearing is one layout step, not a stream of them. Cap at six pills (C6) so the height is bounded by construction.
  • It disappears the moment the chat has a message — the same session.messages.length === 0 gate. The always-available path (C13) is what covers "I wanted it after I'd already sent".
  • Hidden panes are inert. Retained background chats keep this mounted; the hover preview and the read it warms (C8) must be gated on the pane being active, or a pointer crossing the window warms transcripts in chats you are not even looking at.

C5 New Fixes a "Untitled" row

Labels and order — a pill must never read "Untitled"

A chat's title is seeded "Untitled" and only replaced when an AI title lands. There is deliberately no prompt-snippet stage, the request has a 45 s timeout, and it can fail outright. So "a chat with messages but no title" is a normal, reachable state — and it is most likely on the chat you were just in, which is the one you most want to attach.

The query already returns the first user message as summary. Use it as the label when the title is still the seed. Nothing extra to fetch.

Distinguish the two strings: "Untitled" is the stored seed and is load-bearing logic (UNTITLED_TITLE gates discard-vs-archive on close). "Untitled chat" is only an empty-string render fallback.

Ordering — one rule, everywhere
  • Order: chats.created_at DESC — newest chat tab first, oldest last (needs B2). Not last activity: a chat created three weeks ago that an agent is streaming into right now stays exactly where its age puts it.
  • Why creation beats activity here. The row sits above a composer you are about to type into, and it is on screen for seconds. An activity-ordered row re-sorts itself while you look at it, because background chats are streaming — you would reach for the second pill and click the third. Creation order is fixed the moment the tab exists, so the row is the same on every visit, and it matches the mental model of the tab strip you just came from.
  • Same order in the picker (C6) and the "+" menu (C13). One list, one order, three entry points. A second sort in the overflow would mean the pill you couldn't find is not where the row implied it would be.
  • The current chat is excluded via the query's existing excludeChatId.
  • Terminal tabs are excluded for free — they are PTY-backed and write no chat_messages, so the EXISTS clause never matches. Worth a test rather than a comment, since it's incidental.
  • Other workspaces are excluded. The query is folder-scoped, and that is correct: a transcript from a different worktree describes a different tree, and its file paths would mislead the agent.
  • Closed (archived) tabs are included, and not marked as closed. They are frequently the most valuable — you closed the tab because the work finished — and a chat's transcript does not become less useful when its tab is dismissed. Per D5, open-vs-closed is not a grouping, a sort key, or a badge anywhere in this feature; there is one list of chats in creation order. Requires dropping the query's hard-coded archived = 0 (B2).
  • Zero-message chats never appear — the EXISTS clause requires ≥1 user text message. A chat with only a system notice is correctly invisible.
C6 New

Overflow — six pills, then one search field over every chat in the workspace

Six is a deterministic cap, not a measured one: no layout reads, no resize observer, and at any Column-2 width it lands as one or two rows. A workspace with thirty chats gets a bounded row and a real way to find the thirty-first — where the reference would get seven wrapped rows and no search.

The picker is a search field and a list, and nothing else: no section headers, no open/closed split, no timestamps, no sizes. One row is one line — agent mark, chat name, message count — in the same creation order as the row above it. Everything that used to be in the second line of a row now lives in the hover preview (C8), one chat at a time.

Reuse the <Command> primitive inside a <Popover> — same shape as the existing quick-open and history menus, so filtering, keyboard nav and empty-state come for free.

What the row shape buys, and what it costs
  • The picker's first six rows are the row. Same chats, same order, same counts — the popover just keeps going. That is what makes "7 more" an honest label rather than a door into a differently-organised list, and it is why the picker needs no headings to orient you.
  • 26px rows, so twelve fit without scrolling. The two-line row was 46px: the same popover showed six. Halving the row height is the whole reason a flat list works without section headers to break it up.
  • The count is the same number as the pill's, in the same 11px tabular --fg3, on the same trailing edge. A chat you saw in the row and then found in the picker reads as one object, not two records.
  • Already-attached chats show the check, not the count — the same displacement the pill makes (C4), so the picker is a second view of one state rather than a second state.
  • The cost: no date anywhere in the list. With a flat list of thirty chats in creation order, "which of these is recent" is answered by position alone. That is the trade — position is a weaker signal than a timestamp, and it is bought back by the preview, which is one hover away and names the date outright.
Search here is title-and-first-prompt only — a client-side filter over the list already in hand. Do not wire it to messages.search (the FTS5 op): full-text hits would surface chats whose title has nothing to do with the query, and a picker that returns transcripts you don't recognise is worse than one that returns fewer. Filtering must not re-sort either — matches stay in creation order, so the list you filtered is the list you were already reading.
C7 Decided — D1

Concise always — and full one right-click away

Every click attaches the concise transcript. There is no segmented control, no preference, no sticky per-workspace mode — the row's label line is four words and the pills carry one number each. Concise is user-prompt → concluding answer per turn: the decisions, at roughly a tenth of the volume, which is what a fresh agent needs. Full is archaeology — which files, which commands, which tool output.

The escape hatch is a right-click, and it is not a new idea in this app: the chat tab's own context menu already offers Copy concise transcript and Copy full transcript, in that order, under a separator (column2-chat-tabs.tsx:857-864). Same gesture, same two words, same order, one surface over — a user who has ever copied a transcript already knows where full lives.

What the menu has to get right
  • Concise stays in the menu even though a click already does it. Three items cost nothing and the first one is the cheapest possible teach: it names what a plain click costs, so the default stops being a guess.
  • Full replaces, it never adds. Dedupe is by chatId (C9), so choosing Full on an already-added pill swaps the attachment in place. The chip's filename going .concise.txt → .full.txt is the only visible confirmation — which is exactly why the mode lives in the filename.
  • Same two words, same order, same icons as the tab menu. Not "detailed", not "brief"; concise above full; ClipboardList and Copy, lifted straight from column2-chat-tabs.tsx. A second vocabulary for one existing pair of modes is how two mental models start.
  • "Open this chat" goes last, under a separator. It unmounts this whole row by switching tabs, so it must not sit adjacent to the two attach verbs where a mis-aimed click lands on it.
  • It cannot be mouse-only. This menu is the only route to the full transcript, so a keyboard user must reach it from a focused pill. <ContextMenu> opens on the platform's context-menu key (Shift F10) — but macOS has no universal one, so verify this on the machine during commit 3 and, if Electron forwards nothing usable, bind ⌥ Enter on the focused pill as the declared fallback. No new global shortcut either way.
What this decision costs, and what pays for it
  • Right-click is undiscoverable — and it stays that way, deliberately. Nothing on a pill hints there is a menu. Every fix considered puts the chrome back: a chevron, a hover-reveal "⋯", a caption under the row, a line at the foot of the preview panel. All of them charge every user on every pass for a gesture most sessions never need — which is the exact objection that killed the segmented control. Adding it back one font size smaller is not a different decision.
  • What pays for it: the gesture is already in the user's hands. Right-clicking a chat to get its transcript is something this app already does — on the chat tab, with these two words, in this order. The pill's menu is the same gesture on the same object one surface over, so it is found the way the tab menu was found. And a user who never finds it still gets the concise transcript, which is the right answer nearly every time. An undiscovered escape hatch costs nothing; a permanent label costs every render.
  • ⌥-click was rejected, not forgotten. An invisible modifier that silently changes what a click costs is precisely the failure the count on the pill exists to prevent, and it makes mixed-mode attachments possible with nothing on screen distinguishing them. Note this is not the same as the ⌥-Enter fallback above: that one opens the menu, so the two words are still on screen and the choice is still made in the open.
A user who never right-clicks loses nothing. The word "full" appears nowhere in the row, the picker, or the "+" menu — only in this context menu and in a filename after you have asked for it. That is the test the removed segmented control failed: it made every user read a control that most sessions never need.

E Rejected

Considered and rejected

Recorded so the same ideas don't get re-litigated in review.
Reuse <from_previous_chat> / SummaryImport
  • It exists, is agent-agnostic, and was built for precisely this hand-off.
  • But it is invisible context. Nothing in the composer shows it, the sent bubble hides it, and there is no way to remove it once staged.
  • It also sets queuedEditable: false, so a queued send carrying one can no longer be edited — a real, silent capability loss.
  • Its body is the first user message, not a transcript. It answers a different question.
Write the transcript to disk and pass @path
  • Tempting: the prompt stays tiny and the agent reads only what it needs. The image path already does this (.context/attachments/<chatId>/).
  • But it changes the guarantee. "The agent knows what happened" becomes "the agent could find out" — one tool call away, and agents routinely skim or skip. For a context hand-off that's the wrong default.
  • It also leaves files in the worktree for every click, and needs a writeTextAttachment IPC that doesn't exist.
  • Worth revisiting only as an explicit "attach as file reference" mode later.
Use the vendored <Suggestions> wrapper
  • It is the obvious primitive and its own comment says "for empty-state".
  • But it is a horizontal scroller with ScrollBar className="hidden" — options past the fold are undiscoverable, with no count and no affordance.
  • Its px-4 is off the button standard's 10px.
  • Take Button variant="secondary" size="sm" + a wrapping flex row instead.
A dialog / full picker as the primary surface
  • Scales to any number of chats and needs no cap.
  • But it costs a click to discover that there is anything to discover. The whole value here is that five candidates are visible at the moment you're deciding what to type.
  • Kept as the overflow and as the always-on path, which is the right role for it.
Auto-attach the most recent chat
  • Zero clicks; matches the "I always want the last chat" case.
  • But it spends context without being asked, and the most recent chat is often an unrelated one-off. Silent cost is the one thing this design is built to avoid.
Any size or token figure, anywhere
  • Tokens are what actually gets spent, and this audience thinks in them. Bytes are at least exact.
  • But our only conversion is a flat CHARS_PER_TOKEN = 4, wrong by 20–30% on code-heavy transcripts; and a byte figure taken from SUM(LENGTH(payload)) over-states the formatted file by 3–10×, so the pill and the chip would disagree in front of the user.
  • And per D6 the ceiling itself is model-dependent, so any "of 1.0 MB" makes the row a conversation about the model pill. The message count is exact, free, and cannot contradict itself.
A group-level Concise / Full switch
  • Revision 1's recommendation: a 20px segmented control on the label line, making the trade visible at the point the cost is paid.
  • But it charged every user for a choice most sessions never make, on the one line the empty state can least afford to complicate — and once the budget readout went (D6), it had nothing to point at. Concise by default with the alternative on right-click (C7) costs the row zero pixels and reuses a gesture the chat tab already teaches.
Warn when the source chat moved after you attached
  • Revision 1's C10: compare lastMessageAt on every DB tick, swap the chip's glyph for a refresh arrow, offer "6 newer messages since".
  • But it makes every attachment provisional. The user has to decide, per chip, whether "newer" means "better" — with no way to see the difference — and a refresh re-materialises a file they already previewed into one they haven't. A file you attached is a file, and remove-then-re-click is already the whole gesture (D9).
Sort the row by last activity
  • "Most recently worked in" sounds like the most useful order, and it puts the chat you just left leftmost.
  • But it is the one order that moves while you read it: a background agent finishing a turn re-sorts the row under the cursor, and the pill you were reaching for becomes a different chat. Creation order is fixed the moment the tab exists, matches the tab strip, and is backed by the one column the schema deliberately never rewrites (B2).
