Terminal pane · Setup tab · State catalog

Every state the Setup tab can show — and where they should converge

The Setup tab is where a workspace installs its dependencies. Today it shows one thing in a worktree and something different on “main”, and a few states leave the user guessing. This catalog is the full inventory: what ships today, and a before / after for the cases we want to consolidate into one consistent surface.

One Setup surface, one status language Same states, same pill, main and worktrees alike.

One status language

Running, complete, and failed always read the same way — a single status pill — no matter which workspace you opened.

Status that survives

Whether setup last passed or failed is remembered, so reopening or restarting the app never loses the outcome.

Never a dead end

Loading, interrupted, and trimmed-output moments each say what’s happening and always offer the next action.

Part A — States that ship today

The user’s project has no setup script configured. The tab explains what a setup script is, and offers one action — add one — which takes them straight to Settings to configure it.

A3 Ships today

Setup running

Live install output streams into the tab. A “Running…” pill with a spinner sits bottom-right; the Rerun button is disabled while it works. On a freshly created worktree this starts automatically — so it’s usually the first thing the user sees.

Setup failed

The run exited with an error. A red “Setup failed” pill flags it and the error output stays visible so the user can read what went wrong, then “Rerun setup” to try again. A failure doesn’t block the workspace — they can still work in it.

Part B — Gaps to consolidate · before → after

B1 Gap → proposal

“Main” setup shows no status

On the main workspace, running setup drops the user into a plain terminal with no status pill — when it finishes they can’t tell whether it passed or failed, only that it stopped, with a bare “Rerun setup”. In a worktree the same action gives a clear pill. After: main uses the exact same status language as everywhere else.

The single biggest inconsistency to unify.
Before — main today
Run
Setup Terminal
$ pnpm install Packages: +1284 Progress: resolved 1284, reused 1284, added 1284, done Done in 9.1s [process exited — press any key]
After — proposed
Run
Setup Terminal
$ pnpm install Packages: +1284 Progress: resolved 1284, reused 1284, added 1284, done Done in 9.1s
Setup complete
Before: no pass/fail signal, no “Running…” indicator — the user is left reading raw terminal output to guess the outcome.
After: the Running / complete / failed pill (and the tab dot from B6) behave identically on main and in worktrees.
B2 Gap → proposal

Status disappears after an app restart

Setup passed yesterday — but after quitting and reopening the app, the tab shows the blank “No setup output yet” screen as if it never ran. The live log is gone, and the pass/fail result goes with it. After: the last outcome is remembered and shown as a compact summary, with a clear way to run again.

The result is durable; only the streamed log is in-memory.

Before: a passed workspace and a never-run workspace look identical — the user loses the fact that setup already succeeded.
After: the remembered outcome carries the pill forward as a summary card; the same card shows “Setup failed” in red when relevant.
B3 Gap → proposal

Loading & the first-run handoff

Two blank moments: on open the tab can flash “No setup output yet” for an instant before it knows the real state, and after pressing Run it sits on the empty state (with just a spinning button) until the first line of output arrives. After: a brief, honest loading state so the tab never looks empty-but-idle.

Applies to both first paint and first run.

B4 Gap → proposal

Trimmed (very long) output

A big install produces more output than the tab keeps, so the oldest lines are dropped. Today the only hint is a dim line buried mid-log that’s easy to scroll past. After: a small, persistent “earlier output trimmed” chip in the status row makes it obvious the top isn’t the true beginning.

Only the tail of a long run is kept.

B5 Gap → proposal

Interrupted run — output but no result

If the app was quit mid-install, the tab can come back with leftover output but no pass/fail — the run never got to finish. Today that reads as ambiguous: log present, no pill, no explanation. After: a neutral “Setup didn’t finish” state names what happened and offers to run it again.

After: a neutral “didn’t finish” pill (distinct from a real failure) explains the interruption and points at the next step.
B6 Gap → proposal

Setup status isn’t visible on the tab

Setup runs in the background, but the “Setup” tab label looks the same whether it’s installing, done, or broken — the user has to open the tab to find out. After: a small status dot on the tab (spinner while running, green when complete, red when failed) so the state is visible at a glance, matching how the Run and Terminal tabs already show “(exited)”.

Reuses the same three states as the pill.

Part C — Container context

C1 Context · ships today

Worktree missing — the Setup tab isn’t shown

If the workspace folder is deleted from disk, the whole panel — Setup included — is replaced by a recovery screen. Worth noting so the consolidation doesn’t try to render a Setup state that can’t exist here; there’s nothing to set up until the worktree is back.

Panel-level state that supersedes the Setup tab.
Worktree missing
This workspace’s folder is no longer on disk. Restore the folder and refresh, or delete the workspace to reclaim it.
