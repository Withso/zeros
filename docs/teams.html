Teams — how the best do it, and Zeros' plan

Linear, Figma, OpenAI, and Anthropic all converge on the same shape: organization → team, billing on the org, and a default container auto-created for everyone — including individuals. Zeros studied that, then went simpler: one flat level called a Team, created only when asked for. This page distills the study, the schema, the security rules, and the build plan. Full detail with sources: teams.md.

↩︎ Auto-created container: NO (reversed 2026-07-22)

The study said yes; the product said no. Nothing is created at sign-in — a user makes a Team when they want one, and zero teams is a supported state.

↩︎ Two levels: NO (reversed 2026-07-25)

"Organization" is retired from the vocabulary. The old nested sub-team — and its undeletable "Personal" default — was dropped. A Team contains members. That is the whole hierarchy.

✅ Supabase auth-only + Railway PG

Sound and portable — with guard-rails: Railway Pro, PITR on, pinned image, nightly off-platform dumps.

Auth: Supabase signs, Railway decides

1 · LOGIN
Mac app signs in via Supabase (email OTP / GitHub / Google) → gets a JWT signed with Supabase's private key.
2 · VERIFY
Zeros backend on Railway verifies the JWT locally against Supabase's public JWKS — no round-trip, no shared secret.
3 · MIRROR
First request auto-creates the users row (JIT provisioning). No webhooks, no sync drift.
4 · AUTHORIZE
Role looked up in Postgres on every request — JWT proves who, the database decides what.
Lock-in check: passes. The only Supabase surface is "it signs tokens." Swap later to self-hosted GoTrue or another issuer = change two URLs. Schema, backend, record: untouched. Auth is free to 50k monthly-active users ($25/mo Pro recommended so the auth project never pauses).

The schema (12 tables, Railway Postgres)

users (id = Supabase sub, email, soft-delete) teams (slug, name, logo, created_by) — the tenant root team_members (team_id + user_id PK, role: owner|admin|member) invitations (email, role, token_hash — never the raw token, 7-day expiry) team_settings (team-wide + per-repo docs → engine resolve chain) org_secrets (ciphertext only — envelope encryption, key_version) audit_log (append-only: member.invited, secret.updated, …) billing_customers / billing_subscriptions (Stripe mirror = entitlements) cloud_workspaces (+ team_id — the pointer Conductor's DB revealed) — every tenant table carries team_id · RLS on as the second lock —

Security rules that prevent the classic breaches

Invitations

32-byte random token, stored hashed, single-use, 7-day expiry; accept binds to the signed-in account (wrong-account interstitial); identical responses whether an email exists or not.

Secrets vault

Envelope encryption (per-secret data key, master key only in the backend env). Write-only UI. Decrypted once per spawn, injected as env — never in TOML, never in git, never in chat records.

Invariants in SQL

Never zero owners (transaction-checked). Seat limits enforced at invite-accept. All membership changes audited.

Identity on the wire

Message authorship stamped server-side from the verified JWT — never client-supplied. Same JWKS check on backend and engines. Stripe webhooks signature-verified; webhooks are the billing truth.

Railway as the record — approved, with guard-rails

Decision delta (formalized here). The 2026-07-02 note leaned Supabase-as-record with Railway as fallback. This part flips it — allowed by that note's own "any Postgres" escape hatch. Parts 04/07/08 get a dated update. Guard-rails, because Railway Postgres is an unmanaged template (corruption threads on auto-upgrades; HA experimental 2026-03; PITR 2026-05): Pro plan · PITR on day one · pinned image · nightly dump to R2 · re-evaluate at ~1k teams. Plain Postgres = a pg_dump away from any VPS / Fly / RDS — which is also the enterprise self-host story.
