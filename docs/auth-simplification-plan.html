Zeros · Auth Audit & Plan · 2026-07-06

What broke, what I fixed,
and how we simplify auth for good

Two production config bugs — not code bugs — took down sign-in, sign-out, and the API today. One is already fixed live; one needs 30 seconds in your Cloudflare dashboard. Then: fold auth.zeros.build into app.zeros.build so this class of outage can't happen again.

Part 1 · Today's two bugs

Bug 1 — a typo took down web sign-in and sign-out needs you · 30 sec

The sign-in machinery reads AUTH0_DOMAIN (the address of the Auth0 server it sends people to). During today's custom-domain migration it was saved as:

login.zeros.design  → should be →  login.zeros.build

An easy slip — you really do own zeros.design (marketing alias). But the login one doesn't exist in DNS, so:

1Click Continue with GitHub
→
2login.zeros.design
“This site can’t be reached”
1Click Sign out
→
2Session cleared ✓
→
3Auth0 logout at …zeros.design
dead-ends — feels broken

The fix: Cloudflare → Workers & Pages → zeros-auth → Settings → Variables and Secrets → Production → edit AUTH0_DOMAIN to login.zeros.build → Save → Deployments → ⋯ → Retry deployment (env changes only apply to a fresh deployment).

Bug 2 — the API rejected every logged-in user fixed live

The Railway backend (api.zeros.build — teams, invitations) checks who issued each login token. Its AUTH_ISSUER still listed the old Supabase issuers from before the Auth0 migration — so every Auth0 token got 401 Unauthorized, even with a perfect login.

Fixed & redeployed: now https://login.zeros.build/, https://zeros.eu.auth0.com/ (new + old domain, so sessions from before today keep working; drop the old one in a week). Service restarted cleanly, API healthy.

Part 2 · “Did we overcomplicate it?” — yes, by exactly one subdomain

DomainWhat it actually isVerdict
app.zeros.buildThe web app: Launch Zeros, desktop handoff, invites — and your future team & billing settingsKeep — make it the center
auth.zeros.buildA separate mini-site that only shows the Google/GitHub buttons and runs the OAuth danceRemove — fold into app
login.zeros.buildNot a site you host. Auth0's own server wearing your domain (exists so Google says “zeros.build” and cookies stay first-party). Users glimpse it in the address bar for a split secondKeep — it is the identity provider
api.zeros.buildRailway control planeKeep

On “login.zeros.build just be a callback URL”: close — it's the opposite. It's Auth0's front door; the callback is ours and it moves: auth.zeros.build/auth/callback → app.zeros.build/auth/callback.

Why auth.zeros.build deserves to die: the same Auth0 settings live in three places (today's outage was exactly this); it adds a pointless redirect hop; it forces the session cookie to be shared across all *.zeros.build subdomains instead of locked to one; and it's a whole extra deployment for ~5 small files. The two Pages projects already share one session store — they're one app pretending to be two.

Migration — safe, ~half a day, zero user disruption

  • Move the code (one PR): copy the five auth functions into web-app under /auth/*; callback → app.zeros.build/auth/callback; provider buttons inline on the hub; cookie locked to app.zeros.build only; styled error pages with a Try-again button.
  • Config (15 min): Auth0 → add the new callback to Allowed Callback URLs (keep old during transition; logout URL already allowed — tested). Cloudflare → move auth env vars onto zeros-web.
  • Deploy & retire (a week later): test both journeys → auth.zeros.build becomes a permanent redirect → then delete the project, its DNS, the old callback, and the old Railway issuer.
✦ After the merge, the entire auth config is: 4 vars + 1 KV binding on zeros-web, and 3 vars on Railway. One place to typo instead of three — and I couldn't have broken today what wouldn't exist.
