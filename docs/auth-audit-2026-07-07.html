1The two “user lists” — and where the chain breaks

Auth0 is the identity phonebook: a user appears there instantly at first login. Railway is the product record (user + personal org + “Personal” team): it's created just-in-time by the Mac app's first authenticated API call after sign-in.

3Root cause: the token is missing its email stamp

Verified good: Railway runs current main (deployed 06 Jul 17:59 UTC) · issuer/audience env correct · signing keys live · desktop→backend wiring works (the 401s prove calls arrive).

Auth0 access tokens don't carry email by default — a Post-Login Action must stamp https://zeros.build/email + email_verified onto each token, and the backend requires them (fail-closed, an anti-account-takeover control). The website works regardless because it reads the id_token, which carries email natively — exactly why sign-in “looks fine” while the backend rejects everyone.

Prime suspect: the Post-Login Action isn't running in the live tenant — detached from the login flow, un-deployed, or deployed to a different tenant during the custom-domain shuffle. A token decoded on 06 Jul had the claims, yet this morning's fresh sign-in still 401s.

2-minute check: Auth0 dashboard → Actions → Triggers → post-login: is the Action in the flow and Deployed? Then sign in fresh and paste the access token into jwt.ms — does it contain https://zeros.build/email?

4Second bug: your two existing accounts will lock out after the fix

The user_identities table (links github|000000000 → user row) is empty — both existing users predate it. The backend treats “unknown identity + email already exists” as a takeover attempt → 409 rejected on every call. So post-fix: hi@ provisions fine (new email), but sam@example.com and sam.rivera@example.net get locked out of the control plane. One-time backfill:

5Consent pages — normal, nothing to configure

  • The consent screens are GitHub's and Google's own pages — Auth0's extra “Authorize App” interstitial is deliberately suppressed (PR #140). That's the standard first-party UX.
  • Providers ask consent once per (account × app), ever — then silently approve forever.
  • Your hi@ GitHub identity shows 6 logins in Auth0 — today wasn't its first authorization. Consent appeared at its true first login (earlier testing) and never again; with an active GitHub browser session the redirect completes in under a second.
  • Google will ask consent the first time a brand-new Google account signs in — account picker + “wants access to your email & profile” — then never again.
  • Traced the live redirect chain: both connections use your own OAuth apps (GitHub Ov000000000000000000, Google 000000000000-…) — not Auth0 dev keys. The Google page brands as your app, not “auth0.com”. The 06-Jul dev-keys concern is resolved.

6Sign in vs sign up

The current single flow is correct and industry-standard (Linear, Vercel, Notion do the same): first-timers are auto-created (Auth0 instantly; Railway user + personal org + Personal team on the app's first API call), returning users just sign in. The landing page already says “New here? Signing in creates your account.” No separate sign-up screen should be added. It will work end-to-end once §3 + §4 are fixed.
