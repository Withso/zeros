Decision update · 2026-07-02

Two decisions now set the direction

Made after this research landed — decided, not under debate. Every page in the pack is updated to match; where a page previously argued the other way, the original reasoning stays visible under a dated note.

① The cloud record — we go Conductor's way on the database

The cloud record is our cloud database that permanently stores your chats, sessions, and workspace history in your account. The engine stays the live hub while a workspace runs — nothing changes about the live experience or the direct connection — but it now writes through every chat and state event to the record, near-real-time. The picture to keep: the sandbox is the workbench, the cloud record is the filing cabinet, GitHub is the vault. Workbenches get cleared; the filing cabinet doesn't — your history comes back anytime, even years later, even if every sandbox is gone. Local workspaces can sync too — a fast-follow after cloud workspaces ship, with a privacy opt-out. Honest cost: the write-through layer is real engineering, so v1 moves from ~3–5 to ~3.5–6 months; the always-on database itself is cheap. Privacy, stated openly: unlike Conductor's "none of it is stored on our servers", Zeros does keep chat and history in your account in our cloud — that is the feature: encrypted at rest, exportable, deletable on demand.

② Enterprise — they host the record on their servers

For enterprise customers, the same software runs with the cloud record and all workspace data on their infrastructure — their Postgres (the record), their object storage, their git remotes, optionally their sandbox runners. "Your data never lives in our cloud — it lives in yours." Decision ① makes this cleaner, not harder: all durable data lives in exactly one well-defined place, so self-hosting = pointing Zeros at their database. Still built after v1 GA; the seams are designed now, starting with a configurable record endpoint.

How it works

The whole design on one diagram

Two independent "planes" make a cloud workspace feel local: files mirror to your Mac for instant editing; chat and agent state live with the engine in the cloud so any device — and later, any teammate — can connect to the same brain. New since 2026-07-02: the engine streams every chat and state event through to the cloud record, so your history outlives any sandbox.

💻 Your Mac — the Zeros app
The window onto the workspace. Reads files from a local mirror at disk speed.
  • Editor · file tree · diffs → read the local file mirror
  • Chat · terminals · agent controls → talk over the bridge
⇄ secure WebSocketchat · agents · terminal · git status — one always-open encrypted line
⇄ file sync (Mutagen)two-way, working files only — the "fast as local" trick
☁️ The sandbox (Daytona)
A rented Linux computer, created in seconds, disposable by design.
  • Zeros engine — the same brain, running remotely
  • zeros.db — the live working copy of chat & state; writes through to the cloud record
  • Claude Code · Codex · Cursor running as child processes
  • Git worktree — the actual code
🛎️ Control plane — the reception desk
Supabase (login + who-owns-which-workspace registry) and a thin worker that creates/starts/stops sandboxes. Never on the live wire between your Mac and the sandbox.
🐙 GitHub — the vault (code)
Code always lives in the git remote. Destroying a sandbox never loses code.
🗂️ The cloud record — the filing cabinet
Our cloud database (decided 2026-07-02): every chat, session, and workspace history, permanently in your account — synced to every device you log in on. The engine writes through to it as you work. Enterprises can run this on their own servers. Periodic exports to cheap storage remain as a safety-net backup.

💤 Sleep-when-idle: when no agent is running and you've been away ~60 minutes, the sandbox stops (≈$0.001/hr) and wakes when you return. And because history lives in the cloud record, even a deleted sandbox loses nothing — the workbench gets cleared; the filing cabinet doesn't.
