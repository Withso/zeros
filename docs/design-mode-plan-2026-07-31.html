The five foundations (the "basement" — everything later stacks on these)

FoundationWhy it's load-bearing
Frames are plain HTML+CSS files, zero JavaScriptInert documents — safe, diffable, portable, and the format agents are literally trained on. A lint rule bans <script>/event attributes; the only script in a rendered frame is our own editor runtime, injected at render time, never in the file.
The style language is real CSS — nothing inventedNordcraft proved the inspector can be pure views over CSS declarations (size, layout, fill, stroke, effects…), with tooltips naming the real property. Our style editor, the future themes table, and every agent edit share one vocabulary. Their Apache-2.0 CSS parser round-trips text ⇄ controls.
tokens.css = typed tokens + the layout resetDesign tokens as typed @property custom properties (with per-theme values) and a reset layer that makes every element behave like Figma auto-layout (flex column by default). Your future variables/themes table is just a UI over this one file — no new storage ever needed.
Stable element IDs (data-oid)Every element carries a small ID (self-healed by the app). Click-to-select, the layers panel, style writeback, agent tools, and future component instances all address elements through this one scheme.
One mutation + validation layer in the engineAgent file edits, inspector edits, and future structured tools all converge on: validate → minimal file edit → lint → broadcast. Constraints hold no matter who edited.

The design tool layer — your "very, very important" question, answered

✅ It's a native MCP server, and it works for every agent. All three adapters (Claude, Codex, Cursor) already accept per-session MCP servers — and the Zeros engine already runs a real MCP server internally (the gateway). The design server rides the same stack, injected only in design workspaces, workspace-aware (tools resolve against the calling agent's worktree). Future agents inherit it automatically. This is also what the field converged on: paper.design's whole agent story is a local MCP; Figma, Subframe, Webstudio likewise.

The v1 toolset 7 tools

get_selection — what the user has selected on canvas: the context bridge
list_frames · get_frame — orientation + compact tree summaries
screenshot_frame — the agent sees its own work (Phase 2)
lint_design — the constraint engine's voice
get_tokens — the design-system vocabulary
get_guide — the rulebook, loaded on demand

Deliberately small (Cursor caps ~40 tools total). Structured write tools (write_html, update_styles…) arrive with the style editor — thin wrappers over the same mutation layer.

Editing: files first, tools around them

Agents write the HTML/CSS files directly — that's what they're best at (claude.ai's own artifacts are files edited by targeted replacements), and it's fast. The MCP layer supplies what files can't: context, eyes, and rules.

"Agent uses only design tools" is unenforceable for two of three agents (only Claude supports tool bans) — so exclusivity comes from the environment instead: in a sparse design worktree there is nothing else to edit, and the lint loop makes the good path the only passing path.

How constraints actually bind (the four layers)

1 · teachThe contract
system prompt + MCP instructions + get_guide: concrete, checkable rules only
→
2 · checkDesign lint on every change
no scripts, local refs only, valid HTML, known tokens — regardless of who edited
→
3 · correctThe feedback loop
violations return inside tool results; file edits get a turn-end card + auto-follow-up — works for ALL agents
→
4 · hardenHard rules where possible
Claude path denies; the sparse worktree under everything

This is the synthesis of what ships elsewhere: Figma teaches the valid document via skill files with hard gates; Framer's linter gives "instant, absolute feedback"; Vercel's rule — deterministic checks go to linters, judgment goes to guidance; Webstudio validates patches and rejects invalid references before applying.

Components & themes — later, but the basement already fits them

Future featureWhat v1 lays down for it
Components (Figma-like mockup components that are still markup)A reserved components/ folder and zd- tag prefix. The model: a component is an HTML file; an instance is a compact tag like <zd-button label="Get started"> that the renderer expands — files stay pure markup, no JS. Lint's grounding rule (borrowed from v0): an instance is valid only if its definition file exists.
Themes / variables tableTokens are already typed @property entries in tokens.css; themes become attribute-scoped token blocks in the same file. The table is a UI over it — plus get_tokens already hands agents the vocabulary.
Prototype tab, comments, pen/shape toolsRendered in the shell per your mock, disabled in v1; no architectural debt blocks any of them.

Build order

  • The workspace + the loop. Design workspaces end-to-end (sparse worktree, seeded tokens.css), the shell (canvas live-rendering Zeros Design/*.html, chat with no splits, panel scaffolds, pen-tool icon), the design MCP with 6 tools, the lint engine, the agent contract. Exit test: all three agents design, get linted, self-correct on the follow-up, and the frames commit to the design branch.
  • Selection, layers, eyes. Click any element → layers tree + breadcrumb + read-only inspector; selection rides into the chat; screenshot_frame lets agents see and fix their own overflow.
  • The style editor. The inspector becomes editable — instant, token-aware edits written as minimal file diffs with no agent turn; structured MCP writes land as wrappers over the same layer; frame CRUD, inline text, assets.
  • Scale & polish. Served frames (real asset URLs + CSP), contrast/overflow lint tier, PNG export, propose-directions cards, component-model spike, themes table.
